BUG001
Title: Send-a-file-to-a-person works end to end on the backend (via Transfers), but every UI control for it is unwired
Severity: Critical
Details: My Files empty state says "Upload from the desktop app or drag files in," but there is no upload button, no file input, and no drag-drop handler anywhere in the DOM - confirmed with "Show planned features" enabled too, so it is not feature-flag-gated, it is simply not wired up in the frontend.
Tested directly against the API (bypassing the UI) to separate "missing button" from "missing feature":
- POST /d-vault/files/upload -> 200 OK, "Upload completed", file appears correctly in My Files afterward with working Download/Rename/Delete/Star.
- POST /d-vault/transfers with body {fileId, recipientEmail} -> 200 OK, "Transfer created", record appears live on the Transfers screen (status QUEUED, route LAN, recipient email shown).
- POST /d-vault/transfers/{id}/progress?progressPct=25 (query param, not JSON body) -> 200 OK, "Progress updated", status flips to ACTIVE with correct percentage.
- POST /d-vault/transfers/{id}/cancel -> 200 OK, "Transfer cancelled".
- The dedicated share/outbox-style endpoints (/d-vault/files/{id}/share, /d-vault/shares, /d-vault/share/create, /d-vault/outbox, etc.) all return 404 - Transfers, not Share, is the real "send to a person" mechanism in this backend.
Conclusion: the entire send pipeline (upload -> create transfer to a recipient email -> track progress -> cancel) is fully functional server-side. The gap is 100% frontend: the "+ New transfer" button (Transfers), the file upload control (My Files), and the per-transfer "+25%"/"Cancel" buttons all fire zero network requests when clicked (see BUG006). Once these are wired to the existing endpoints above, the core SEND -> Inbox -> Conversation workflow should work.
Data-quality note found in testing: transfer records created via the API come back with fileName: null, sizeBytes: 0, and direction: null even though a valid fileId was supplied - the transfer isn't populating these fields from the linked file record.
Robustness note: sending a malformed/incorrectly-shaped body to POST /d-vault/transfers or POST /d-vault/transfers/{id}/progress returns a raw 500 "Something went wrong" instead of a 400 validation error - these endpoints don't validate input defensively.

BUG002
Title: Dashboard crashes blank after visiting Notifications/My Files then Dashboard
Severity: Critical
Details: Console error confirmed: "Uncaught TypeError: (v.data ?? []).filter is not a function". A paginated API response (e.g. /d-vault/notifications?page=0&size=50) likely returns an envelope object ({content, page, size, totalElements}) instead of a bare array. A Dashboard widget reads the same cached query key expecting a plain array and calls .filter() directly on the wrapper object, throwing during render. No error boundary catches it, so the whole page goes blank. Only a manual refresh (clears client cache) fixes it. Reproduces by navigating Notifications (or another paginated list) then Dashboard.

BUG003
